# Backend Schema — NutriResQ

## 1. Purpose and design principles

This document defines the proposed PostgreSQL model for scenarios, road networks, food donations, recipient organizations, vehicles, optimization runs, algorithm outputs, and benchmark measurements.

The schema should support a small but credible single-operator CCP MVP. Donors, recipients, and vehicles are initially **data records**, not mandatory login roles. User accounts and organization portals are not required unless explicitly added to scope.

### Principles
- PostgreSQL on Neon is the system of record.
- Use normalized source records and explicit foreign keys.
- A run must preserve a snapshot of the exact inputs used.
- Store detailed results separately from mutable scenario inputs.
- Use constraints for basic data integrity and application validation for cross-record/algorithm rules.
- Use migrations; do not modify the hosted schema manually without recording the change.
- Use parameterized SQL through `pg`.
- Keep timestamps in `timestamptz` and store them consistently in UTC.
- Do not store credentials or secrets in domain tables.

## 2. Entity relationship overview

```text
locations ─────┬──── roads (from_location_id, to_location_id)
               ├──── donors ──── donations
               └──── recipients

scenarios ─────┬──── scenario_changes
               ├──── optimization_runs ──── vehicle_allocations
               │                           ├── routes ──── route_stops
               │                           └── algorithm_benchmarks
               └──── scenario input records / scenario membership
```

**Important modeling choice:** a location is a reusable geographic record; a scenario controls which records and road/donation/vehicle states are active for a particular experiment. The first implementation may store scenario-specific records directly or use explicit scenario membership/override tables. Pick one model before writing migrations and keep it consistent. The proposed MVP below uses scenario-owned operational records where this simplifies snapshots, with `locations` as reusable locations.

## 3. Core tables

The definitions below are a logical schema proposal, not a migration file. Final SQL types, names, and constraints should be checked when migrations are written. Use UUID primary keys generated by the application or PostgreSQL consistently; do not mix key strategies without reason.

### 3.1 `locations`

Represents geographic nodes such as donor sites, recipient sites, or other network points.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `name` | `text` | Required, non-empty |
| `location_type` | `text` | Controlled values such as `donor`, `recipient`, `hub`, `other` |
| `latitude` | `double precision` | Required; range -90 to 90 |
| `longitude` | `double precision` | Required; range -180 to 180 |
| `projected_x` | `double precision` | Optional projected coordinate used for planar closest-pair calculation |
| `projected_y` | `double precision` | Optional projected coordinate used for planar closest-pair calculation |
| `created_at` | `timestamptz` | Required default current timestamp |
| `updated_at` | `timestamptz` | Required default current timestamp |

Use `projected_x`/`projected_y` only if the chosen coordinate projection and units are documented. Do not calculate kilometer distances directly from latitude/longitude degree differences and label them as kilometers.

### 3.2 `roads`

Represents a graph edge between locations.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `scenario_id` | `uuid` | FK to `scenarios.id` if roads are scenario-owned |
| `from_location_id` | `uuid` | FK to `locations.id` |
| `to_location_id` | `uuid` | FK to `locations.id` |
| `cost` | `numeric` or `double precision` | Required, finite and non-negative |
| `cost_unit` | `text` | For example `km` or `cost_points`; choose consistently |
| `is_available` | `boolean` | Required; false means closed/unavailable |
| `is_bidirectional` | `boolean` | Required; define how the graph builder interprets it |
| `created_at` | `timestamptz` | Required |
| `updated_at` | `timestamptz` | Required |

Constraints:
- `from_location_id <> to_location_id`, unless self-loops are deliberately supported.
- Prevent duplicate edges according to the chosen directionality policy.
- Closed roads remain stored but are excluded from the graph for that run.
- The edge cost must match the cost units used by A\* and ACO.

### 3.3 `donors`

Represents a food-donation source.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `scenario_id` | `uuid` | FK to `scenarios.id` if scenario-owned |
| `location_id` | `uuid` | FK to `locations.id` |
| `name` | `text` | Required |
| `donor_type` | `text` | For example `restaurant`, `bakery`, `supermarket`, `other` |
| `is_active` | `boolean` | Required |
| `created_at` | `timestamptz` | Required |
| `updated_at` | `timestamptz` | Required |

The MVP can use synthetic donor records. Do not add login credentials to this table.

### 3.4 `recipients`

Represents a recipient organization and its modeled need/priority.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `scenario_id` | `uuid` | FK to `scenarios.id` if scenario-owned |
| `location_id` | `uuid` | FK to `locations.id` |
| `name` | `text` | Required |
| `recipient_type` | `text` | For example `shelter`, `food_bank`, `community_kitchen`, `welfare_org`, `other` |
| `demand_units` | `integer` or `numeric` | Non-negative; units must be documented |
| `priority_score` | `integer` or `numeric` | Documented range and meaning |
| `is_available` | `boolean` | Required |
| `created_at` | `timestamptz` | Required |
| `updated_at` | `timestamptz` | Required |

If package value depends on recipient priority, document how the priority influences package value. Do not apply the same priority twice accidentally.

### 3.5 `donations`

Represents a donation batch or package that can be considered by the allocation algorithm. If a donation must be split across vehicles, the package model must explicitly support split quantities; otherwise each row represents an indivisible package.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `scenario_id` | `uuid` | FK to `scenarios.id` if scenario-owned |
| `donor_id` | `uuid` | FK to `donors.id` |
| `package_name` | `text` | Required |
| `weight_units` | `integer` | Positive integer in the documented DP scale |
| `value_score` | `integer` | Non-negative integer objective value for DP |
| `recipient_id` | `uuid`, nullable | Optional intended recipient if the model supports directed donations |
| `available_at` | `timestamptz` | Optional |
| `expires_at` | `timestamptz` | Optional; define whether equality with run time means expired |
| `is_eligible` | `boolean` | Required |
| `status` | `text` | Controlled values, e.g. `available`, `expired`, `reserved`, `unavailable` |
| `created_at` | `timestamptz` | Required |
| `updated_at` | `timestamptz` | Required |

Rules:
- `weight_units > 0`.
- `value_score >= 0`.
- Expiry eligibility is evaluated against a documented run timestamp.
- A package that cannot fit any available vehicle is reported as oversized.
- If fractional weights are required, define a conversion scale (e.g. 0.1 kg per DP unit) and use it consistently. The scale is a product decision, not an implicit rounding operation.

### 3.6 `vehicles`

Represents a vehicle available for allocation and routing.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `scenario_id` | `uuid` | FK to `scenarios.id` if scenario-owned |
| `name` | `text` | Required |
| `capacity_units` | `integer` | Positive integer in the same weight scale used by DP |
| `start_location_id` | `uuid` | FK to `locations.id` |
| `is_available` | `boolean` | Required |
| `created_at` | `timestamptz` | Required |
| `updated_at` | `timestamptz` | Required |

The initial model assumes one capacity dimension (weight). If volume, refrigeration, or multiple capacity dimensions are later added, revise the algorithm model and schema together.

### 3.7 `scenarios`

Represents a named experiment/data configuration.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `name` | `text` | Required |
| `description` | `text` | Optional |
| `status` | `text` | Controlled values such as `draft`, `ready`, `archived` |
| `parent_scenario_id` | `uuid`, nullable | Self-FK for a simulated/copied scenario |
| `created_at` | `timestamptz` | Required |
| `updated_at` | `timestamptz` | Required |

A scenario identifies the data configuration being edited. A run snapshot captures the exact inputs used at execution time. If the final implementation chooses a scenario-membership/override model instead of scenario-owned rows, document that before migrations.

### 3.8 `scenario_changes`

Records changes applied during simulation.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `scenario_id` | `uuid` | FK to the simulated scenario |
| `source_run_id` | `uuid`, nullable | FK to the run used as the comparison baseline |
| `change_type` | `text` | Controlled type such as `close_road`, `reduce_capacity`, `expire_donation`, `disable_vehicle`, `disable_recipient` |
| `target_entity_type` | `text` | Entity type being changed |
| `target_entity_id` | `uuid` | ID of the affected record; validate it belongs to the scenario |
| `before_value` | `jsonb` | Prior value(s) for audit/review |
| `after_value` | `jsonb` | New value(s) |
| `created_at` | `timestamptz` | Required |

The `jsonb` fields are for change descriptions, not a substitute for normalized primary data. Validate change types and values in the service layer.

### 3.9 `optimization_runs`

One record per integrated optimization attempt.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `scenario_id` | `uuid` | FK to `scenarios.id` |
| `parent_run_id` | `uuid`, nullable | FK to `optimization_runs.id` for before/after lineage |
| `status` | `text` | `running`, `succeeded`, `partial`, `failed` |
| `input_snapshot` | `jsonb` | Immutable normalized inputs used for the run |
| `algorithm_config` | `jsonb` | Algorithm names, parameters, versions, seed where relevant |
| `metrics` | `jsonb` | Summary metrics with documented units |
| `warnings` | `jsonb` | Structured warning array |
| `error_code` | `text`, nullable | Safe stable code for failed run |
| `error_message` | `text`, nullable | Safe summary; no secrets or stack traces |
| `started_at` | `timestamptz` | Required |
| `completed_at` | `timestamptz`, nullable | Set on completion/failure |
| `created_at` | `timestamptz` | Required |

The `input_snapshot` is central to reproducibility. Reopening a run must not reconstruct its original inputs from mutable current scenario records alone.

### 3.10 `vehicle_allocations`

One row for each package assignment made in a run.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `run_id` | `uuid` | FK to `optimization_runs.id` |
| `vehicle_id` | `uuid` | FK to the vehicle record or snapshot reference |
| `donation_id` | `uuid` | FK to donation record or snapshot reference |
| `assigned_weight_units` | `integer` | Positive; equals package weight if indivisible packages |
| `value_score` | `integer` | Value used by the optimizer |
| `created_at` | `timestamptz` | Required |

Constraints:
- unique `(run_id, donation_id)` if each package is indivisible and assigned at most once;
- no allocation row for an unassigned package;
- application-level post-validation ensures sum of assigned weights per vehicle does not exceed its run-snapshot capacity.

For robust history, keep the original names and key facts in the run snapshot or store explicit snapshot labels on result rows so deleted/edited current records do not make old runs unreadable.

### 3.11 `routes`

One row per vehicle route in a run.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `run_id` | `uuid` | FK to `optimization_runs.id` |
| `vehicle_id` | `uuid` | FK to vehicle record or snapshot reference |
| `status` | `text` | `complete`, `partial`, `infeasible`, `not_required` |
| `total_cost` | `numeric` or `double precision` | Non-negative for feasible legs; unit documented |
| `cost_unit` | `text` | Same road-cost unit as graph |
| `algorithm_name` | `text` | For example `aco` |
| `algorithm_config` | `jsonb` | Parameters and seed where relevant |
| `created_at` | `timestamptz` | Required |

A route cost must be recalculated from its road legs. Do not trust a client-supplied total.

### 3.12 `route_stops`

Ordered stops for a route.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `route_id` | `uuid` | FK to `routes.id` |
| `sequence_number` | `integer` | Positive, unique per route |
| `location_id` | `uuid` | FK to `locations.id` or snapshot location |
| `stop_type` | `text` | Controlled values such as `start`, `pickup`, `delivery`, `other` |
| `related_donation_id` | `uuid`, nullable | FK if stop corresponds to a donation |
| `related_recipient_id` | `uuid`, nullable | FK if stop corresponds to a recipient |
| `leg_cost_from_previous` | `numeric` or `double precision`, nullable | Null for first stop; documented units |
| `leg_path` | `jsonb` | Ordered road node/edge identifiers or a stable snapshot representation |
| `created_at` | `timestamptz` | Required |

Constraint: unique `(route_id, sequence_number)`. Define the route's pickup/delivery semantics before implementing route generation. If the first version models only delivery stops, document that simplification explicitly.

### 3.13 `algorithm_benchmarks`

Stores comparison measurements.

| Column | Suggested type | Rules / meaning |
|---|---|---|
| `id` | `uuid` | Primary key |
| `run_id` | `uuid`, nullable | FK to related optimization run |
| `scenario_id` | `uuid` | FK to scenario |
| `algorithm_name` | `text` | Required |
| `baseline_name` | `text`, nullable | Baseline if this row represents a comparison |
| `input_fingerprint` | `text` | Identifies comparable normalized inputs |
| `configuration` | `jsonb` | Parameters, seed, repeat/trial details |
| `result_summary` | `jsonb` | Objective value, path cost, pair distance, or relevant result |
| `runtime_ms` | `numeric` | Non-negative measured runtime |
| `memory_bytes` | `bigint`, nullable | Only if measured reliably |
| `trial_number` | `integer` | Positive if repeated trials are stored |
| `created_at` | `timestamptz` | Required |

Comparison rule: algorithm and baseline must run on equivalent inputs and conditions. A benchmark must identify the metric being compared; runtime alone does not prove better solution quality.

## 4. Relationship summary

- One scenario can have many runs and scenario changes.
- One scenario contains or references many locations, roads, donors, donations, recipients, and vehicles according to the chosen scenario-data model.
- One run belongs to one scenario and can have a parent run for comparison lineage.
- One run can have many vehicle allocations, routes, and benchmark rows.
- One route belongs to one run and vehicle and has ordered route stops.
- Each donation can be assigned at most once per run in the indivisible-package model.

## 5. Data types, units, and constraints

Before writing migrations, explicitly decide and document:

1. **Road cost:** distance, time, or abstract cost points. All edges and route totals must use compatible units.
2. **Package weight:** unit and integer scaling for DP. Example: if a DP unit represents 0.1 kg, 3.4 kg becomes 34 units; only use such a scale if it is approved and applied consistently.
3. **Package value:** a non-negative integer score or another precisely defined objective.
4. **Recipient demand:** units and how it affects package selection or fulfillment metrics.
5. **Coordinates:** latitude/longitude for map display; projected coordinates or a documented geographic distance method for closest-pair calculations.
6. **Expiry semantics:** define whether `expires_at <= run_started_at` means the package is expired.
7. **Directionality:** whether each road row is directed or bidirectional and how reverse edges are built.
8. **Package indivisibility:** if a package can be split, change constraints, assignment rows, and DP model together.

Use database `CHECK` constraints for basic numeric ranges and `NOT NULL` constraints for required fields. Application validation is still needed for graph connectivity, eligibility, aggregate vehicle capacity, scenario ownership, and algorithm state limits.

## 6. Index recommendations

Add indexes based on the actual query patterns and confirm them with measurements. Likely candidates:

- `roads(scenario_id, is_available)`;
- `roads(from_location_id)` and `roads(to_location_id)`;
- `donations(scenario_id, status, expires_at)`;
- `vehicles(scenario_id, is_available)`;
- `recipients(scenario_id, is_available)`;
- `optimization_runs(scenario_id, created_at DESC)`;
- `vehicle_allocations(run_id, vehicle_id)`;
- `routes(run_id, vehicle_id)`;
- `route_stops(route_id, sequence_number)`;
- `algorithm_benchmarks(scenario_id, created_at DESC)`.

Avoid adding every possible index without a use case; indexes increase write and storage costs.

## 7. Transactions and consistency

Saving a completed run should use a transaction for related writes:

1. insert or update run status and snapshot;
2. insert allocations;
3. insert routes and ordered stops;
4. insert benchmark rows if part of the same operation;
5. update final metrics/status and completion timestamp;
6. commit only if the result set passes integrity checks.

On failure, roll back related writes where appropriate and persist a safe failure status through a separate controlled transaction if needed. Never leave a run marked `succeeded` with missing result rows.

## 8. Migrations and seed data

Recommended migration order:

1. create shared `locations`;
2. create `scenarios`;
3. create scenario-owned operational tables (`roads`, `donors`, `recipients`, `donations`, `vehicles`) with their foreign keys;
4. create `scenario_changes`;
5. create `optimization_runs`;
6. create `vehicle_allocations`, `routes`, and `route_stops`;
7. create `algorithm_benchmarks`;
8. add indexes, check constraints, and any deferred foreign keys required by the final model.

The final ordering may differ if scenario membership/override tables are chosen instead. Make dependencies explicit in the migration sequence.

Seed only synthetic, clearly labeled data. The seed dataset should include enough variety to demonstrate:
- at least one route with multiple stops;
- a closed road;
- a disconnected or unreachable case;
- a donation that expires or is ineligible;
- a package too large for the available fleet;
- more eligible food than total fleet capacity; and
- multiple vehicles with different capacities.

## 9. Privacy and access

The MVP can operate without donor/recipient accounts. Do not create authentication tables merely because donor and recipient entities exist. If authentication is later required, design it separately with password/session handling, role boundaries, and access rules. Never store plaintext passwords or session secrets in these domain tables.

The API must ensure a caller cannot edit arbitrary records by submitting another scenario's IDs. Enforce scenario ownership/association in services and database constraints where possible.

## 10. Schema decisions that must be resolved before migrations

- scenario-owned rows versus shared records with scenario membership/overrides;
- whether all route stops include both pickups and deliveries or only the simplified delivery stops;
- whether packages are indivisible;
- the exact DP integer scale and value formula;
- whether route/road costs use kilometers, time, or abstract units;
- the closest-pair coordinate projection and units;
- whether result tables reference mutable source rows, store snapshots, or both; and
- the exact enum/check-constraint strategy.

Do not let an AI agent silently decide these in SQL. Resolve the choices in this document and keep implementation/tests aligned.
